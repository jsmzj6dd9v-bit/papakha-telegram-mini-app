# Обновление рабочего места менеджера

Подготовлены фильтры «Требуют действия», «Новые», «Мои сделки», «Ожидаем клиента», «Все активные» и «Архив», серверная пагинация по 25 записей, обновление списка раз в 15 секунд, мобильные карточки и панель сделки с вкладками.

Действия выдаёт backend в `availableActions`. Данные карточки включают `revision` — число неизменяемых событий. Изменяющие запросы отправляют `expectedRevision` и `expectedUpdatedAt`. Сервер проверяет статус и ответственного; D1 batch атомарно фиксирует контрольную запись операции и все изменения/уведомления. Проигравший конкурентный запрос не оставляет побочных записей.

Добавлены `GET /api/admin/team`, фильтры `view`, `offset` существующего списка и действие `POST /api/admin/deals/:id/transfer` с `adminId` и `reason`. Менеджеры видят все заявки, изменяют только свои; владелец может передавать чужие заявки. Для взятия используется ID авторизованного сотрудника.

## Порядок выпуска

1. Применить добавочную миграцию `0004_admin_operations.sql` в D1. Существующие заявки не переписываются.
2. Развернуть backend и проверить авторизованный список, карточку, роли и передачу на тестовой заявке.
3. Развернуть admin-worker вместе с новым `workflow-ui.js`.
4. Проверить вход владельца и менеджера в Telegram, обработку тестовой сделки и уведомления без реальных переводов.

Предыдущие версии Workers сохранить для отката. При откате интерфейса новая таблица может остаться. GitHub Pages Mini App для этого обновления менять не требуется.

## Локальный просмотр

Из `admin-worker` запустить `node preview.mjs`, затем открыть `http://127.0.0.1:8091`. Это отдельный сервер с демонстрационными данными в памяти. Изменяющие запросы отклоняются; он не использует рабочую базу и Telegram. Этот сервер не входит в статические файлы админки.

Проверены 20 backend-тестов и 2 теста admin-worker. Новые тесты используют SQLite с настоящими миграциями и транзакционной моделью D1 batch. Реальные мобильные Telegram-клиенты и production-публикация требуют отдельной проверки после выпуска.
